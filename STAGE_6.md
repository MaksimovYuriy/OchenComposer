# Этап 6: понимание метафор через внешний API

Статус: интеграция реализована по поручению владельца. Реальный API и качество
интерпретаций пока не проверены без личного ключа; требуется ручная приёмка.
Этот документ дополняет ITERATIONS.md и не меняет исходное ТЗ. AI разрешён для
анализа метафор; выбор API — наше решение для реализации, не требование задания.

## Назначение и границы

Пользователь вводит метафору или заголовок. Готовая языковая модель выбирает подходящие
предметы из фиксированного каталога и коротко объясняет интерпретацию. Собственную
модель не обучаем. Не ограничиваем смысловой подбор тремя заранее заданными запросами.

Поток: фраза → внешний API → проверенный план scene-v2 → исполнитель scene-plan.ts
→ локальная перекраска → редактируемая композиция → SVG.
Названия по-прежнему используют отдельную компоновку 5A.

Модель не рисует новые предметы и не возвращает paths/SVG/код. Теперь задаёт экземпляры,
нормализованные координаты, разрешённые повороты, слои и опоры. Отдельные масштабы
и произвольные цвета запрещены. L/S, формат и палитра остаются настройками пользователя.
Точный сценарий названий остаётся отдельным и работает без ключа и сети.

## Доступ и передача на проверку

Принят вариант с личным API-ключом пользователя (BYOK). Проверяющий получает сборку
плагина и инструкцию, регистрируется у провайдера, создаёт свой ключ и вводит его
в настройках. Запросы расходуют его квоту. Наш сервер для этой схемы не нужен.

Вариант с общим сервером обсуждался, но для текущей поставки не выбран. Общий ключ
не встраиваем в код плагина. Установка плагина сама по себе не выдаёт доступ к модели:
для проверки метафор нужен действующий ключ, доступность API и свободная квота.

Предварительный кандидат — OpenRouter с бесплатной моделью. В обсуждении проверена
публичная квота 50 запросов/день; это ориентир для прототипа, не обещание постоянного
лимита. Перед реализацией повторно сверить условия, доступность аккаунта/региона,
доступные модели и поддержку формата ответа. При необходимости рассмотреть Groq;
поддержку нескольких провайдеров сразу не считаем обязательной частью этапа.
Gemini обсуждался как альтернатива с региональными ограничениями, не выбран.

Используем только явно выбранную бесплатную модель, без автоматической платной
замены. Ограничение запросов/токенов и нагрузка сервиса могут остановить обработку.
Результат объясняется пользователю, не маскируется успешной случайной сценой.

## Настройки ключа

- Поле со скрытыми символами; ключ вводится в интерфейсе плагина.
- Кнопка проверки подключения с понятным результатом; проверка может расходовать квоту.
- По умолчанию хранение в памяти до закрытия плагина.
- Явная опция «Запомнить на этом устройстве» и команда удаления сохранённого ключа.
  Локальное хранилище настроек не позиционируется как защищённый менеджер секретов.
- Ключ не включается в сборку, каталог, scene/pluginData, SVG, логи и сообщения об ошибках.
  Провайдер получает его для авторизации запроса через HTTPS.

Ранее записанное ограничение «ключ не попадает в клиент» заменено: при BYOK ключ
находится в клиенте по выбору пользователя. Запрещено распространять общий секрет
в клиентской сборке, а не использовать введённый самим пользователем ключ.

## Что отправляется внешнему сервису

1. Введённая пользователем метафора или заголовок.
2. Минимальный текстовый каталог: разрешённый ID, название, смысловые ассоциации,
   допустимые состояния. Например: book — книга, знания/обучение;
   lamp — лампа, идея/открытие; puzzle — пазлы, решение/взаимодействие.
3. Числовые размеры и разрешённые углы выбранной детализации, формат/seed.
4. Инструкция выбирать только из каталога, ограничение количества и структура ответа.

Не отправляются SVG-файлы, векторные контуры, изображения/превью, примеры из
assets/examples, скриншоты, дерево документа Figma, названия страниц, сторонние
объекты пользователя и содержимое его файла. Для смыслового подбора они не нужны.
Исходники загружает и использует локальный плагин, не модель.

Это означает отсутствие передачи иллюстраций в API, а не отсутствие передачи данных
вообще: текст фразы и текст каталога получает внешний сервис. Если используется
агрегатор, обработка может включать выбранного им провайдера модели. Правила хранения
и использования текста зависят от условий этих сервисов; нулевое хранение не обещаем.
В интерфейсе до отправки должно быть понятно, какие текстовые данные уходят наружу.
Запрос отправляется при явном запуске обработки, не при каждом вводимом символе.

## Ответ модели и локальная проверка — обновление scene-v2

Прежний metaphor-v1 с main/support заменён на scene-v2 по поручению владельца:
ИИ возвращает готовые настройки композиции. Пример минимальной сцены:

```json
{
  "status": "ok",
  "items": [{"instanceId":"i1","assetId":"book","x":0.5,"y":0.5,"rotation":0,"layer":0,"on":null}],
  "explanation": "Книга выражает обучение."
}
```

Ровно status/items/explanation; максимум 8 экземпляров. Повторы assetId разрешены,
instanceId и layer уникальны. Для отказа status:unsupported, items:[]. Проверяются
положения, повороты, опоры и пересечения. Полный контракт и ограничения — SCENE_PLAN.md.
Состояния задаются локально; объяснение не гарантирует понимания текста моделью.

Плагин независимо проверяет типы, обязательные поля, размер ответа, разрешённые ID,
состояния и общий лимит 1–8 предметов. Не выполняет код из ответа, не импортирует
предложенные моделью ресурсы и не подставляет неизвестные компоненты. Правила повторов
фиксируются в схеме; дополнительные экземпляры не появляются неявно.

Только полностью проверенный план исполняется. Ответ не может обходить ограничения
геометрии, относительных размеров и палитры.
Объяснение показывается пользователю, выбранные предметы доступны для дальнейшей правки.

## Порядок разработки

1. Проверить доступность выбранного API и подобрать конкретную бесплатную модель.
2. Описать текстовые ассоциации всех компонентов; согласовать минимум 12 запросов:
   4 прямых темы, 4 метафоры, 4 неоднозначных/неподдерживаемых запроса.
   Для каждого заранее описать допустимые интерпретации, не единственную сцену.
3. Зафиксировать JSON-контракт и валидатор, затем адаптер провайдера отдельно
   от существующего компоновщика. Промпт и контракт должны иметь версию.
4. Добавить настройки ключа, проверку подключения и режим метафор.
   Разрешить в manifest только необходимые сетевые адреса выбранного сервиса.
5. Обработать неверный ключ, исчерпанную квоту, сетевой сбой, таймаут, отказ модели,
   повреждённый JSON, неизвестный ID, повторное нажатие и устаревший ответ.
   Не создавать частичные сцены и не изменять предыдущую композицию при ошибке.
6. Пройти тестовый набор с реальным API и отдельно автоматические проверки адаптера
   на подставных ответах без секретов. Проверить фактический состав исходящего запроса.
7. Подготовить инструкцию проверяющему и пройти путь с его собственным ключом:
   подключение → произвольная метафора → объяснение/композиция → правка → SVG.
8. Приёмка владельцем → исправления → повторная проверка. Разрешение обсудить и
   записать этап не считается подтверждением приёмки 5A или готовности этапа 6.

## Приёмка

- Все 12 запросов пройдены; неподдерживаемые и неоднозначные случаи объясняются честно.
- Модель выбирает только существующие предметы, конструктор сохраняет векторность,
  геометрию, общий масштаб, L/S, палитру и возможность ручной правки.
- Исходящие запросы не содержат SVG/изображений/документа; ключ не оказывается в
  сцене, экспорте, логах и поставляемых исходниках.
- Ключ проверяющего работает независимо от ключа разработчика; сохранение только
  по явному выбору, удаление и режим сессии проверены.
- При сетевых ошибках, лимитах и неверном ответе нет случайной композиции,
  платного переключения, частичного результата или повреждения старого фрейма.
- Прямые названия работают офлайн. Ограничения бесплатного API и порядок получения
  ключа описаны в инструкции сдачи. Качество оценивается владельцем на реальных результатах.
